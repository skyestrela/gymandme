# Gym&Me WSL Test Instance

## Purpose

This is a working **test** instance for exercising Gym&Me in Android Chrome/PWA before the durable production deployment is ready. It is not the permanent hosted service and must not be treated as a migration target for an existing Gym&Me account.

## Verified current route

- HTTPS URL: `https://ax16pro-wsl-new.tail07c964.ts.net/`
- Exposure: Tailscale Funnel is enabled. This URL is publicly reachable while Funnel remains on.
- Frontend: Vite development server on local port `5173`.
- API: Gym&Me Node API on local port `3000`.
- State directory: `$HOME/.local/share/gymandme-test`.
- Process supervision: enabled user units `gymandme-api.service` and
  `gymandme-web.service`.
- API WebAuthn values:
  - `RP_ID=ax16pro-wsl-new.tail07c964.ts.net`
  - `ORIGIN=https://ax16pro-wsl-new.tail07c964.ts.net`
  - `RP_NAME=Gym&Me`

The API health response was opened after setup and returned one user. Registration was then re-started with `INVITE_ONLY=1`; a read-back of `/api/config` confirmed `invite_only: true`.

## What has been verified

1. `tailscale funnel status` shows the HTTPS hostname proxying to `http://127.0.0.1:5173`.
2. `GET /api/health` through the HTTPS hostname returns `200` and reports one user.
3. `GET /api/config` through the HTTPS hostname returns `200` and reports `invite_only: true`.
4. The Vite module served through HTTPS contains the pinned exercise image/GIF CDN bases.
5. A real Android user opened the instance and created the initial profile.
6. Both Gym&Me user units are enabled and active; the HTTPS health endpoint
   still returns one user after the manual processes were replaced.
7. A deliberate restart of both user units briefly returned `502` while Vite
   reconnected to the API, then recovered to HTTPS health `{ "ok": true,
   "users": 1 }` with registration still invite-only.

## Android testing flow

1. Open the HTTPS URL in Chrome.
2. Sign in with the passkey created for this hostname.
3. Chrome menu → **Add to Home screen** / **Install app**.
4. Log a test workout and bodyweight entry.
5. Test a reload and an offline restart only after the HTTPS app has opened completely once online.
6. Export a backup before any destructive test.

## Operator commands

Run these only from the local Gym&Me checkout and only after checking current listeners/processes.

### Normal operation

The test instance is supervised by user systemd units, not terminal-owned
processes:

```bash
systemctl --user status gymandme-api.service gymandme-web.service --no-pager
systemctl --user restart gymandme-api.service gymandme-web.service
```

The unit definitions are:

```text
~/.config/systemd/user/gymandme-api.service
~/.config/systemd/user/gymandme-web.service
```

They are enabled under the existing linger-enabled user manager. Verify the
HTTPS health endpoint after any Windows/WSL reboot; Funnel exposure remains a
separate Tailscale configuration.

### Start the API

```bash
cd api
env \
  PORT=3000 \
  DATA_DIR="$HOME/.local/share/gymandme-test" \
  RP_ID=ax16pro-wsl-new.tail07c964.ts.net \
  ORIGIN=https://ax16pro-wsl-new.tail07c964.ts.net \
  RP_NAME='Gym&Me' \
  FIRST_USER_ADMIN=1 \
  INVITE_ONLY=1 \
  ALLOW_GUEST=0 \
  AUDIT_LOG=0 \
  npm start
```

### Start the frontend

```bash
cd frontend
API_ORIGIN=https://ax16pro-wsl-new.tail07c964.ts.net \
  npm run dev -- --host 0.0.0.0 --port 5173 --strictPort
```

### Check the instance

```bash
curl --fail https://ax16pro-wsl-new.tail07c964.ts.net/api/health
curl --fail https://ax16pro-wsl-new.tail07c964.ts.net/api/config
sudo tailscale funnel status
```

## Safety boundaries

- Funnel is public. Do not put private production data into this test instance.
- Disable public exposure when testing is paused or complete:

```bash
sudo tailscale funnel --https=443 off
```

- The existing account on another Gym&Me server does not automatically transfer here. Pairing codes can only be generated by the original server that holds that account; local-only data requires an export/import backup.
- This is still a Vite-based WSL test instance, not a final production deployment. The API/web
  processes are user-systemd-managed, but the public Funnel route and post-reboot HTTPS behavior
  must be re-verified after a Windows/WSL restart.
- The intended socialbee deployment remains blocked while its root filesystem is full; do not deploy Gym&Me there until storage is remediated and the host is re-verified.
